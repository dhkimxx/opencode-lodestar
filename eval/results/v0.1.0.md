# Evaluation results for v0.1.0

Measured on 2026-10-17 with OpenCode 2.0.27 and the harness in [`eval/`](../README.md).

## Setup

- **Scenarios.** The five scenarios in `eval/scenarios/`. Each run copies a small project, drives a real OpenCode session through two or three turns, compacts it at fixed points, and checks the result with tests the agent never saw. Automatic compaction is set to start at 60,000 tokens.
- **Configurations.** A is OpenCode alone. B is OpenCode with lodestar at commit `79babc1`.
- **Models.** `opencode-go/longcat-2.5-preview-free` ran each scenario three times per configuration, plus three more runs of S3, the one scenario where results differed. `opencode-go/mimo-v2.5` ran each scenario once per configuration as a cross-check.
- **A note on beam-free.** The plan named `opencode-go/beam-free` as the main model. It hit its rate limit overnight and stayed limited, so the final code was measured with longcat instead. Earlier beam-free runs are where the problems listed under "What evaluation changed" turned up.

- Restoring (T2) is what cuts the files read again after compaction. Without it, they more than double.
- The summary lodestar writes (T3) showed no benefit in these tasks, while it added output tokens and time. Whether to keep it, drop it, or add its instructions to OpenCode's own summary request instead is the main question for the next version.
- The recap reminder (T4) and the changed-file notice (T6) showed no clear effect either way. S4 is the only scenario where T6 can act.

## What evaluation changed

Each of these came from a run that went wrong, and each was fixed before the final measurements.

- **No message after compaction.** lodestar first posted a one-line note after each compaction. OpenCode counts such a message as a new exchange, so the next compaction kept the turn before it as serialized text, and in that text beam-free started writing its own tool-call syntax into tool arguments until the provider rejected the conversation. Across 53 runs with the note, 13 showed this; 12 of them had the serialized text. Without the note, compaction behaves as it does without lodestar.
- **Markdown, not XML.** Restored files used `<file path="…">`, and a model copied `path="…"` into a tool argument. Restored files and skills are now headings and fenced blocks.
- **No todo tool.** The agent never called it in 55 runs, and its first-turn tool calls broke twice only while it was offered. It was removed.
- **Not the whole project.** With a few files restored, agents stopped searching the code and missed uses in files they never opened. The restoration now lists the session's other files and asks for a search before changes that may reach other files.
- **One snapshot per summary.** Snapshots were matched to summaries by their first 300 characters, and two summaries that opened the same way shared one. They are matched by a hash of the whole summary.

## Limitations

- With these models, OpenCode alone already finishes most tasks, so most of lodestar's effect shows in effort, such as files read again and prompt tokens, more than in success.
- Samples are small: three to six runs per scenario and configuration.
- The summary lodestar writes is a separate request. It costs output tokens and time, and unlike OpenCode's own summary request it can't reuse the conversation's prompt cache.
